# Повторная сборка демо APK

Зафиксировано 2026-11-08 после первой автономной сборки. Читать перед следующим
запросом на APK вместе с началом `PROJECT_MEMORY.md`.

## Текущая задача и готовая основа

Пользователь уточнил: это **демо для бизнес-заказчиков**. Ожидаются небольшие
корректировки и повторная выдача установочного APK. Обязательное требование
сохраняется: календарь работает с первого запуска без интернета и сервера.
Подготовка к публикации в магазине сейчас в задачу не входит.

Уже выполнено; заново реализовывать это не требуется:

- React/Capacitor UI и утверждённый логотип D подключены к Android-проекту.
- Python-движок, DE421, часовые пояса и зависимости включены в APK через
  Chaquopy. Сборка поддерживает Android 7.0+, arm64-v8a и x86_64.
- `Back/calendar_service.py` используется веб-адаптером и локальным движком;
  `CalendarEnginePlugin` вызывает расчёты в фоновом потоке. В APK нет HTTP
  адаптера календаря и разрешения INTERNET.
- UTC-начала годов 1900–2052 подготавливаются при сборке для ускорения запуска.
  Это часть действующего процесса; не отключать генератор ради экономии времени.
- Это debug APK с тестовой подписью. Для обновления поверх установленного демо
  сохранять application ID и тот же ключ подписи.

Подробная архитектура и первоначальная настройка: [mobile-development.md](mobile-development.md).

## Почему предыдущая попытка была долгой

Главная работа заключалась в замене серверной архитектуры автономной: выделение
движка, интеграция Python в Android, подбор Android-совместимых библиотек и
сравнение результатов с прежним календарём. Дополнительно скачивались зависимости
и образы Android, выполнялись нативные проверки.

Программные эмуляторы работали без доступного KVM. Проверки WebView, смена образа
Android и повторные запуски заняли существенное время. WebView падал до выполнения
кода приложения; контрольная старая сборка на Android 35 падала так же. Полный
нативный UI остаётся непроверенным; это ограничение среды, а не доказанная причина
ошибки в приложении. При обычной пересборке демо не повторять этот цикл вслепую.

Последняя **Gradle-сборка** прошла за **19 секунд**, 11 задач выполнены,
142 уже актуальны (`/tmp/calendar-offline-final-build.log:216–217`). Это
измерение одной сборки с готовыми кэшами, не обещание времени всего процесса.

## Что сохранить и проверить перед сборкой

Готовое локальное окружение находится в `/tmp/calendar-android-tools/`;
его описание — `environment.json`. Пути временные: после перезагрузки проверить
их существование и восстанавливать только отсутствующее.

| Компонент | Готовое расположение / версия |
| --- | --- |
| JDK 21 | `/tmp/calendar-android-tools/jdk-21.0.13+9` |
| Android SDK, platform/build-tools 36 | `/tmp/calendar-android-tools/sdk` |
| Gradle wrapper 8.14.3 и кэши | `Front/android/gradlew`, `/tmp/calendar-android-tools/gradle` |
| Каталог Android и debug-ключ | `/tmp/calendar-android-tools/android-user/debug.keystore` |
| Python упаковки | `/usr/bin/python3.12` |
| Python расчёта UTC-таблицы | `Back/.venv/bin/python` |
| Эфемерида | `Back/de421.bsp` |

Не удалять SDK, Gradle-кэши, `node_modules`, `.venv`, каталоги сборки или debug-ключ
при обычной корректировке демо. Ключ — локальный секрет, не коммитить и не выводить
его содержимое. Если временное окружение утрачено, время восстановления учитывать
отдельно от времени компиляции.

## Обычная пересборка после правки UI или текстов

Из корня репозитория, используя существующее окружение:

```bash
export JAVA_HOME=/tmp/calendar-android-tools/jdk-21.0.13+9
export ANDROID_HOME=/tmp/calendar-android-tools/sdk
export ANDROID_SDK_ROOT="$ANDROID_HOME"
export ANDROID_USER_HOME=/tmp/calendar-android-tools/android-user
export GRADLE_USER_HOME=/tmp/calendar-android-tools/gradle

cd Front
npm test
npm run android:sync
cd android
./gradlew --offline --no-daemon :app:assembleDebug
```

`android:sync` уже включает TypeScript-проверку, мобильную Vite-сборку и Capacitor
sync. Не запускать перед ним ещё одну одинаковую `build:mobile`. `npm install` /
`npm ci` нужны при отсутствии или изменении зависимостей, не при каждой сборке.
Веб-сборка и запущенный backend для формирования APK не нужны.

Если менялся только нативный код/Python, а упакованный UI актуален, повторять
Vite-сборку не требуется. При изменении Capacitor-плагинов выполнить sync.
`--offline` использует готовые Gradle-кэши; если новой зависимости там нет,
загрузить именно её обычной сборкой с сетью, не переустанавливать весь SDK.
В среде Codex запросить штатное разрешение на Gradle/сеть, если требует sandbox.

## Проверки соразмерно изменениям

| Изменение | Необходимая проверка |
| --- | --- |
| Тексты, цвета, размеры, расположение | Frontend-тесты и TypeScript, просмотр затронутого экрана в браузерной dev-версии, сборка APK |
| Логика экрана, события, переходы | Дополнительно целевой сценарий и соответствующие тесты |
| Расчёты, Python-библиотеки, UTC-таблица | Backend-регрессии, сравнение результатов, нативная offline-проверка движка |
| Мост Java/Python, упаковка, разрешения | Проверка содержимого APK и целевой нативный тест; чистый запуск без сети |

Для каждой выдачи проверить подпись, выравнивание, автономные метаданные и отсутствие
INTERNET в итоговом APK. Использовать `apksigner.jar` через конкретную Java:

```bash
# Из Front/android
"$JAVA_HOME/bin/java" -jar "$ANDROID_HOME/build-tools/36.0.0/lib/apksigner.jar" verify --verbose app/build/outputs/apk/debug/app-debug.apk
"$ANDROID_HOME/build-tools/36.0.0/zipalign" -c -P 16 4 app/build/outputs/apk/debug/app-debug.apk
"$ANDROID_HOME/build-tools/36.0.0/aapt" dump permissions app/build/outputs/apk/debug/app-debug.apk
```

В `assets/public/mobile-build.json` должны быть `offline: true`,
`dataSource: "embedded-python"`, без API URL; в Capacitor config — без server URL.
Данные и Python-архивы проверять повторно при изменении их упаковки.

Если нужен AndroidTest, использовать **`:app:assembleDebugAndroidTest`**.
Корневая `assembleDebugAndroidTest` также собирает тесты стороннего Cordova-модуля
и в прошлый раз привела к конфликту Kotlin. Для обычного демо этот шаг не нужен.
При неизменном движке не скачивать новые образы Android и не повторять полный
набор нативных тестов. При повторении известного сбоя WebView сохранить журнал,
сообщить ограничение проверки и продолжить выдачу APK; новые попытки оправданы
новой причиной или изменившейся средой.

## Выдача и условие завершения

Готовый файл: `Front/android/app/build/outputs/apk/debug/app-debug.apk`.
Предыдущий автономный APK: 102 677 115 байт, приблизительно 103 МБ; размер новой
сборки может отличаться. Большой размер обусловлен включённым движком и данными.

Для прежней локальной ссылки скопировать **новый** файл в
`/tmp/calendar-test-mockup/kyrgyz-calendar-offline.apk`; если используется старый
псевдоним `kyrgyz-calendar-debug.apk`, обновить и его. Сверить SHA-256 копии с
результатом сборки. Проверить HTTP 200 по
`http://127.0.0.1:54597/kyrgyz-calendar-offline.apk`, если сервер запущен.
При отсутствии сервера восстановить только раздачу файлов, не приложение целиком.

Завершать после нужных проверок и выдачи проверенного APK с кратким перечнем
изменений и реальными ограничениями проверки. Не добавлять в задачу демо
настройку магазина, релизного ключа, новые ABI, оптимизацию размера или полный
аудит. Не трогать веб-интерфейс. Не коммитить без запроса пользователя.

## Сохранённые результаты первой автономной сборки

- 13 frontend-файлов тестов прошли; 5 тестов сервиса и 10 регрессий лунного
  календаря/Рамадана прошли. Полные эталонные ответы совпали для пяти случаев.
- Android 35: два instrumentation-теста прошли в авиарежиме без INTERNET,
  включая локальные расчёты 1900/2026/2050; журнал —
  `/tmp/calendar-offline-android-test-optimized.log`.
- Подпись, выравнивание 16 КБ, обе ABI, модули, DE421 и 153 UTC-начала годов
  проверены. Запуск UI на физическом телефоне ещё не подтверждён.
- Проверка собранного UI в Chromium с подменой контракта моста прошла. Она
  проверяет интерфейс отдельно и не заменяет настоящий Android-тест.
- Временные журналы и эталоны могут исчезнуть. Их отсутствие само по себе
  не требует заново проводить всю валидацию при правке текста.
